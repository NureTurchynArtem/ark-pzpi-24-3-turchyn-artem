3 ОПИС ВИКОНАНОЇ РОБОТИ
     У ході роботи розроблено серверну частину програмної системи керування дозволеними діями мобільного застосунку через апаратний помічник: спроєктовано та створено реляційну базу даних, реалізовано функції роботи з нею на основі об’єктно-реляційного відображення (ORM) і прикладний програмний інтерфейс у стилі REST для взаємодії з клієнтами.
     Документ Vision & Scope описує систему загалом, включно з наступними випусками. Відповідно до його розділу 3.1 у цій роботі реалізовано зберігання даних і API для функцій FE-1 (реєстр користувачів і пристроїв), FE-2 (каталог дозволених дій), FE-5 (життєвий цикл команди), FE-6 (прийом подій від пристрою), а також базові складники FE-7 (рольова модель доступу) і FE-8 (журнал аудиту). Обробка намірів за допомогою великої мовної моделі, розрахунок ризику, обмеження частоти виконання дій і функції адміністрування належать до бізнес-логіки серверної частини та будуть реалізовані в лабораторній роботі № 3, а програмне забезпечення IoT-клієнта – у лабораторній роботі № 4.
     Відеозапис перевірки роботи серверної частини наведено в додатку А, графічні матеріали – у додатку Б, фрагменти програмного коду – у додатку В, специфікацію API – у додатку Г.
     3.1 Архітектура серверної частини
     Серверну частину побудовано як модульний моноліт на платформі Node.js з фреймворком NestJS і мовою TypeScript. Застосовано багаторівневу архітектуру: рівень представлення (контролери приймають HTTP-запити, перевіряють вхідні дані та права доступу), рівень сервісів (сервіси виконують операції з даними та перевіряють правила їх узгодженості) і рівень доступу до даних (ORM TypeORM відображає класи-сутності на таблиці СУБД PostgreSQL). Кожен рівень звертається лише до нижчого, тому зміна способу зберігання даних не впливає на контролери, а зміна формату API не впливає на сервіси.
     Функціональність поділено на модулі за предметними сутностями: auth (вхід користувачів і перевірка токенів), users (користувачі та ролі), devices (апаратні помічники), actions (каталог дозволених дій), sessions (сесії взаємодії), commands (команди та їхній життєвий цикл), events (прийом подій від IoT-клієнта), audit (журнал аудиту) і health (перевірка стану сервера). Усі модулі мають однакову будову: контролер визначає маршрути, сервіс працює з базою даних, а класи DTO (Data Transfer Object) описують структуру вхідних даних і перевіряють її за допомогою бібліотеки class-validator.
     Наскрізні механізми налаштовано глобально в точці входу застосунку: конвеєр ValidationPipe відхиляє запити з некоректними або зайвими полями, фільтр DatabaseExceptionFilter перетворює помилки PostgreSQL про порушення обмежень цілісності на відповіді з кодами 400 і 409, модуль @nestjs/swagger формує специфікацію API у форматі OpenAPI 3.0, а механізм CORS дозволяє звернення від вебклієнта наступних випусків.
     Взаємодія з клієнтами відбувається через протокол HTTP у форматі JSON. На поточному етапі клієнтами є тестові клієнти (Swagger UI, Postman, сценарій автоматизованої перевірки), що діють від імені користувачів, та IoT-клієнт – апаратний помічник на ESP32. Користувачі автентифікуються за JWT-токеном у заголовку Authorization, а пристрій – за секретним ключем у заголовку X-Device-Key. У базі даних зберігаються лише хеш пароля (bcrypt) і хеш ключа пристрою (SHA-256), а аудіо голосових запитів на сервер не передається – зберігається тільки текст запиту.
     Фізичне розміщення компонентів системи показано на діаграмі розгортання (рис. 1). Сервер застосунку взаємодіє з СУБД PostgreSQL 16 через TCP/IP; під час розроблення СУБД і вебінтерфейс Adminer для перегляду даних запускаються в контейнерах Docker за допомогою Docker Compose, а параметри підключення задаються у файлі .env.
Рисунок 1 – Діаграма розгортання програмної системи
     Порівняно з документом Vision & Scope для роботи з базою даних замість Prisma обрано ORM TypeORM. TypeORM інтегрований з NestJS через офіційний модуль @nestjs/typeorm, описує таблиці класами-сутностями з декораторами, як і решта коду серверної частини, генерує міграції на основі цих класів і надає конструктор запитів QueryBuilder для складних вибірок.
     Для підтримки інтернаціоналізації час зберігається в стовпцях типу TIMESTAMP WITH TIME ZONE і передається у форматі ISO 8601 в UTC, для кожного користувача зберігаються мова інтерфейсу (uk або en) і часовий пояс, назви дій і параметрів зберігаються українською та англійською мовами, а для стовпців назв задано правила сортування ICU (uk-x-icu та en-x-icu), завдяки яким літери Ґ, Є, І, Ї впорядковуються відповідно до українського алфавіту.
     3.2 Моделі системи та прецеденти використання
     Основні прецеденти використання серверної частини показано на UML-діаграмі прецедентів (рис. Б.1, додаток Б). Абстрактний актор «Користувач» входить у систему та переглядає каталог дозволених дій; від нього успадковуються актори «Оператор», «Адміністратор каталогу» та «Адміністратор системи». Оператор відкриває й завершує сесії, створює команди, змінює їхній стан і переглядає власні сесії та команди. Адміністратор каталогу керує каталогом дозволених дій, а адміністратор системи, крім того, керує користувачами та апаратними помічниками, переглядає журнал аудиту й журнал подій пристроїв. Актор-система «Апаратний помічник» надсилає на сервер окремі події та пакети подій. Технічно сесії та команди доступні користувачам будь-якої ролі, а перелік дій, дозволених кожній ролі, визначає таблиця action_roles, тому на діаграмі ці прецеденти пов’язано з оператором як основним виконавцем.
     Відношення включення «include» показують обов’язкові кроки прецедентів: створення команди завжди включає перевірку прав і параметрів, зміна стану – перевірку допустимого переходу, керування каталогом – опис параметрів і ролей дії, а надсилання подій – перевірку ключа пристрою. Відношення розширення «extend» показує, що відкликання ключа є необов’язковим варіантом керування апаратними помічниками.
     У системі використовуються такі моделі (сутності):
     ˗ роль – довідник ролей (оператор, адміністратор каталогу, адміністратор системи) з назвами двома мовами;
     ˗ користувач – працівник компанії з обліковими даними, роллю, мовою інтерфейсу та часовим поясом;
     ˗ апаратний помічник – IoT-пристрій із серійним номером, хешем секретного ключа, станом і версією прошивки, який може бути закріплений за користувачем;
     ˗ дозволена дія – елемент каталогу з унікальним кодом, назвами, рівнем ризику та ознакою доступності;
     ˗ параметр дії – типізований параметр з одиницею вимірювання та допустимим діапазоном значень;
     ˗ сесія – епізод роботи користувача із системою через апаратний помічник або тестовий клієнт;
     ˗ команда – запит на виконання дозволеної дії в межах сесії з ключем ідемпотентності, станом і кодом результату;
     ˗ значення параметра команди – значення конкретного параметра в конкретній команді;
     ˗ подія пристрою – локальна подія апаратного помічника (натискання кнопки, дотик, оберт енкодера, результат виконання);
     ˗ запис аудиту – незмінний запис про адміністративну операцію.
     Між моделями визначено зв’язки трьох типів: «один до багатьох» (роль і користувачі, користувач і сесії, сесія і команди, дія і параметри, дія і команди, команда і значення параметрів, пристрій і події), «нуль або один до багатьох» (користувач і закріплені за ним пристрої, пристрій і сесії, команда і події, користувач і записи аудиту) та «багато до багатьох» (дозволені дії та ролі, яким їх дозволено виконувати).
     3.3 ER-модель даних
     Структуру даних на концептуальному рівні описано ER-діаграмою (рис. Б.2), побудованою в нотації «пташиної лапки» (Crow’s Foot). Прямокутники позначають сутності з переліком атрибутів, ключовий атрибут підкреслено. Лінії позначають зв’язки, підпис лінії називає зв’язок, а символи на кінцях лінії задають кардинальність: дві риски – рівно один, риска з колом – нуль або один, «лапка» з колом – нуль або багато, «лапка» з рискою – один або багато.
     Особливістю моделі є зв’язок «багато до багатьох» між сутностями «Дозволена дія» і «Роль»: дія має бути дозволена принаймні одній ролі, а роль може мати будь-яку кількість дозволених дій. Сутність «Значення параметра» пов’язує команду з параметром дії та не має власного ідентифікатора – її однозначно визначає пара «команда, параметр». Необов’язкові зв’язки (пристрій без власника, сесія без пристрою, подія без команди) дають змогу зберігати дані тестових клієнтів і службові події пристрою.
     3.4 Структура та нормалізація бази даних
     На основі ER-діаграми спроєктовано 11 таблиць бази даних (табл. 1). Кожну сутність відображено на окрему таблицю, зв’язок «багато до багатьох» між діями та ролями реалізовано проміжною таблицею action_roles зі складеним первинним ключем, а значення параметрів команд – таблицею command_parameters зі складеним первинним ключем (command_id, parameter_id). Службова таблиця typeorm_migrations зберігає історію виконаних міграцій.
Таблиця 1 – Таблиці бази даних
Таблиця Призначення Ключі та обмеження
roles Довідник ролей PK id; UNIQUE code
users Користувачі системи PK id; UNIQUE email; FK role_id → roles
devices Апаратні помічники PK id; UNIQUE serial_number, key_hash; FK owner_id → users
actions Каталог дозволених дій PK id; UNIQUE code
action_parameters Параметри дій PK id; UNIQUE (action_id, code); CHECK діапазону; FK action_id → actions
action_roles Ролі, яким дозволено дію PK (action_id, role_id); FK → actions, roles
sessions Сесії взаємодії PK id; CHECK періоду; FK user_id → users, device_id → devices
commands Команди PK id; UNIQUE idempotency_key; FK session_id → sessions, action_id → actions
command_parameters Значення параметрів команд PK (command_id, parameter_id); FK → commands, action_parameters
device_events Події пристроїв PK id; UNIQUE (device_id, event_uid); CHECK seq ≥ 0; FK → devices, commands
audit_logs Журнал аудиту PK id; FK user_id → users
     Цілісність даних забезпечують обмеження на рівні СУБД: первинні ключі (сурогатні ключі типу SERIAL), зовнішні ключі, обмеження унікальності, NOT NULL і CHECK, а також значення за замовчуванням: now() для часу створення, «uk» для мови, «Europe/Kyiv» для часового поясу, «ACTIVE» для стану пристрою, «CREATED» для стану команди. Допустимі значення мови, стану пристрою, рівня ризику, типу параметра, стану команди та типу події задано перелічуваними типами PostgreSQL (ENUM).
     Правила видалення для зовнішніх ключів обрано відповідно до призначення даних: RESTRICT – для записів з історією (користувач із сесіями, пристрій із подіями, дія, використана в командах), CASCADE – для залежних частин (параметри дії, зв’язки дії з ролями, значення параметрів команди), SET NULL – для необов’язкових посилань (власник пристрою, автор запису аудиту, команда в події). Для прискорення вибірок створено індекси за зовнішніми ключами та полями фільтрації, зокрема (status, created_at) для журналу команд і (device_id, seq) для журналу подій.
     Схему бази даних зведено до третьої нормальної форми:
     ˗ перша нормальна форма (1NF): усі значення атомарні, повторюваних груп немає, кожна таблиця має первинний ключ; параметри дії та значення параметрів команди винесено в окремі таблиці замість зберігання списку в одному полі, а ролі, яким дозволено дію, – у таблицю action_roles;
     ˗ друга нормальна форма (2NF): у таблицях зі складеним ключем неключові атрибути залежать від усього ключа – значення value в таблиці command_parameters визначається одночасно командою і параметром, таблиця action_roles неключових атрибутів не має, а решта таблиць мають простий первинний ключ;
     ˗ третя нормальна форма (3NF): транзитивних залежностей немає – у таблиці commands зберігається лише session_id, а користувач і пристрій визначаються через сесію; назви ролей зберігаються лише в таблиці roles; спосіб підтвердження команди не зберігається в таблиці actions, оскільки він обчислюється з рівня ризику бізнес-логікою.
     Таблиця audit_logs містить пару entity_type та entity_id без зовнішнього ключа: журнал аудиту має зберігати записи й після видалення сутності, на яку вони посилаються, тому це свідоме проєктне рішення. Діаграму структури бази даних з усіма таблицями, стовпцями, типами даних, ключами та обмеженнями наведено на рис. Б.3 і Б.4. Схему створює міграція TypeORM, згенерована на основі класів-сутностей (команда npm run db:migrate), а сценарій наповнення (npm run db:seed) додає демонстраційних користувачів, пристрої, каталог дій, сесію, команди та події.
     3.5 Функції роботи з базою даних
     Доступ до бази даних реалізовано за допомогою ORM TypeORM. Кожну таблицю описано класом-сутністю з декораторами @Entity, @Column, @ManyToOne, @OneToMany і @ManyToMany, які задають назви стовпців, типи, обмеження та зв’язки (лістинг В.1 у додатку В).      3.6 Прикладний програмний інтерфейс
     Для взаємодії серверної частини з клієнтами обрано архітектурний стиль REST. Дані системи природно описуються як ресурси (користувачі, пристрої, дії, сесії, команди, події), над якими виконуються CRUD-операції, тому REST дає просту й передбачувану структуру адрес і методів HTTP. REST не потребує спеціальних бібліотек на клієнті, що важливо для IoT-клієнта на ESP32 зі стандартним HTTP-клієнтом, і підтримує стандартні коди стану та кешування. GraphQL доцільний для багатьох різнотипних клієнтів зі складними вкладеними вибірками, а gRPC потребує HTTP/2 і генерування клієнтського коду, що ускладнює його використання на мікроконтролері та в браузері.
     API має базову адресу /api і обмінюється даними у форматі JSON у кодуванні UTF-8. Методи HTTP використовуються за призначенням: GET – читання, POST – створення, PUT – повне оновлення редагованих полів ресурсу, PATCH – зміна окремого стану (відкликання ключа, завершення сесії, зміна стану команди), DELETE – видалення.      3.7 Специфікація API
     Специфікацію API сформовано у форматі OpenAPI 3.0 автоматично на основі анотацій контролерів і класів DTO. Інтерактивна документація Swagger UI доступна за адресою /api/docs, специфікація у форматі JSON – за адресою /api/docs-json, а її копію збережено в репозиторії у файлі docs/openapi.json. Загальні правила API:
     ˗ користувач автентифікується заголовком Authorization: Bearer <токен>; токен видає ендпоінт POST /api/auth/login, термін його дії становить 3600 с;
     ˗ пристрій автентифікується заголовком X-Device-Key із секретним ключем, який видається один раз під час реєстрації пристрою;
     ˗ списки підтримують параметри page (за замовчуванням 1) і limit (від 1 до 100, за замовчуванням 20) та повертають об’єкт з полями items, total, page і limit;
     ˗ дата й час передаються у форматі ISO 8601 в UTC, наприклад 2026-11-22T09:15:00.000Z;
     ˗ у разі помилки повертається об’єкт з полями statusCode і message; використовуються коди 200, 201, 204, 400, 401, 403, 404, 409 і 503.
     Опис кожного ендпоінту з параметрами, форматом запиту та відповіді, кодами помилок і прикладами використання наведено в додатку Г.

216   /** Зіставляє передані значення з описом параметрів дії та перевіряє їх */
217   private resolveParameters(
218     definitions: ActionParameter[],
219     input: CommandParameterValueDto[],
220   ): Array<{ parameterId: number; value: string }> {
221     const byCode = new Map(
222       definitions.map((definition) => [definition.code, definition]),
223     );
224     const codes = input.map((item) => item.code);
225     const unknown = codes.filter((code) => !byCode.has(code));
226     if (unknown.length > 0) {
227       throw new BadRequestException(
228         `Unknown parameters: ${unknown.join(', ')}`,
229       );
230     }
231     if (new Set(codes).size !== codes.length) {
232       throw new BadRequestException(
233         'Each parameter can be specified only once',
234       );
235     }
236     const missing = definitions
237       .filter(
238         (definition) =>
239           definition.isRequired && !codes.includes(definition.code),
240       )
241       .map((definition) => definition.code);
242     if (missing.length > 0) {
243       throw new BadRequestException(
244         `Missing required parameters: ${missing.join(', ')}`,
245       );
246     }
247     return input.map((item) => {
248       const definition = byCode.get(item.code) as ActionParameter;
249       this.assertValueMatches(definition, item.value);
250       return { parameterId: definition.id, value: item.value };
251     });
252   }

254   /**
255    * Перевіряє, що значення відповідає типу параметра та допустимому діапазону
256    */
257   private assertValueMatches(definition: ActionParameter, value: string): void {
258     if (definition.type === ParameterType.STRING) {
259       return;
260     }
261     if (definition.type === ParameterType.BOOLEAN) {
262       if (value !== 'true' && value !== 'false') {
263         throw new BadRequestException(
264           `Parameter ${definition.code} must be true or false`,
265         );
266       }
267       return;
268     }
269     const numeric = Number(value);
270     const isNumber = value.trim() !== '' && Number.isFinite(numeric);
271     if (
272       !isNumber ||
273       (definition.type === ParameterType.INTEGER && !Number.isInteger(numeric))
274     ) {
275       throw new BadRequestException(
276         `Parameter ${definition.code} must be ${definition.type.toLowerCase()}`,
277       );
278     }
279     const belowMin =
280       definition.minValue !== null && numeric < definition.minValue;
281     const aboveMax =
282       definition.maxValue !== null && numeric > definition.maxValue;
283     if (belowMin || aboveMax) {
284       const min = definition.minValue ?? '-inf';
285       const max = definition.maxValue ?? '+inf';
286       throw new BadRequestException(
287         `Parameter ${definition.code} must be in range [${min}; ${max}]`,
288       );
289     }
290   }

54         .insert()
55         .into(DeviceEvent)
56         .values(rows)
57         .orIgnore()

11 /** Коди помилок PostgreSQL (SQLSTATE), які обробляє фільтр */
12 const PG_UNIQUE_VIOLATION = '23505';
13 const PG_FOREIGN_KEY_VIOLATION = '23503';
14 const PG_CHECK_VIOLATION = '23514';
15 const PG_INVALID_TEXT_REPRESENTATION = '22P02';

17 /** Поля помилки драйвера pg, які використовуються для формування відповіді */
18 interface PgDriverError {
19   code?: string;
20   detail?: string;
21   constraint?: string;
22 }
23
24 /**
25  * Перетворює помилки PostgreSQL (порушення обмежень цілісності) на зрозумілі
26  * HTTP-відповіді,
27  * щоб клієнт отримував 400/409 з поясненням замість 500.
28  */
29 @Catch(QueryFailedError)
30 export class DatabaseExceptionFilter implements ExceptionFilter {
31   private readonly logger = new Logger(DatabaseExceptionFilter.name);
32
33   catch(exception: QueryFailedError, host: ArgumentsHost): void {
34     const context = host.switchToHttp();
35     const request = context.getRequest<Request>();
36     const response = context.getResponse<Response>();
37     const driverError = exception.driverError as PgDriverError;
38     const { status, message } = this.mapError(driverError, request.method);
39
40     if (status === HttpStatus.INTERNAL_SERVER_ERROR) {
41       this.logger.error(exception.message, exception.stack);
42     }
43     response.status(status).json({
44       statusCode: status,
45       message,
46       constraint: driverError.constraint ?? null,
47       path: request.url,
48       timestamp: new Date().toISOString(),
49     });
50   }
51
52   /** Визначає HTTP-статус і текст повідомлення за кодом помилки PostgreSQL */
53   private mapError(
54     error: PgDriverError,
55     method: string,
56   ): { status: number; message: string } {
57     switch (error.code) {
58       case PG_UNIQUE_VIOLATION:
59         return {
60           status: HttpStatus.CONFLICT,
61           message: `Duplicate value. ${error.detail ?? ''}`.trim(),
62         };
63       case PG_FOREIGN_KEY_VIOLATION:
64         // Для DELETE це означає, що на запис посилаються інші записи,
65         // для POST/PUT — що вказаного пов'язаного запису не існує
66         return method === 'DELETE'
67           ? {
68               status: HttpStatus.CONFLICT,
69               message: `Record is still in use. ${error.detail ?? ''}`.trim(),
70             }
71           : {
72               status: HttpStatus.BAD_REQUEST,
73               message: `Related record not found. ${error.detail ?? ''}`.trim(),
74             };
75       case PG_CHECK_VIOLATION:
76         return {
77           status: HttpStatus.BAD_REQUEST,
78           message: `Check constraint violated: ${error.constraint}`,
79         };
80       case PG_INVALID_TEXT_REPRESENTATION:
81         return {
82           status: HttpStatus.BAD_REQUEST,
83           message: 'Invalid value format',
84         };
85       default:
86         return {
87           status: HttpStatus.INTERNAL_SERVER_ERROR,
88           message: 'Database error',
89         };
90     }
91   }

 1 import {
 2   CanActivate,
 3   ExecutionContext,
 4   Injectable,
 5   UnauthorizedException,
 6 } from '@nestjs/common';
 7 import { JwtService } from '@nestjs/jwt';
 8 import { AuthenticatedRequest, JwtPayload } from '../auth.types';
 9
10 /**
11  * Перевіряє JWT-токен із заголовка «Authorization: Bearer <token>»
12  * і зберігає дані користувача в request.user.
13  */
14 @Injectable()
15 export class JwtAuthGuard implements CanActivate {
16   constructor(private readonly jwtService: JwtService) {}
17
18   async canActivate(context: ExecutionContext): Promise<boolean> {
19     const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
20     const token = this.extractToken(request.headers.authorization);
21     if (!token) {
22       throw new UnauthorizedException('Missing bearer token');
23     }
24     try {
25       const payload = await this.jwtService.verifyAsync<JwtPayload>(token);
26       request.user = {
27         id: payload.sub,
28         email: payload.email,
29         role: payload.role,
30       };
31       return true;
32     } catch {
33       throw new UnauthorizedException('Invalid or expired token');
34     }
35   }
36
37   /** Виділяє токен із заголовка Authorization */
38   private extractToken(header?: string): string | null {
39     const [type, token] = header?.split(' ') ?? [];
40     return type === 'Bearer' && token ? token : null;
41   }
42 }

13 /**
14  * Автентифікує апаратний помічник за секретним ключем із заголовка X-Device-
15  * Key.
16  * У базі даних зберігається лише SHA-256 хеш ключа.
17  */
18 @Injectable()
19 export class DeviceKeyGuard implements CanActivate {
20   constructor(
21     @InjectRepository(Device) private readonly devices: Repository<Device>,
22   ) {}
23
24   async canActivate(context: ExecutionContext): Promise<boolean> {
25     const request = context.switchToHttp().getRequest<AuthenticatedRequest>();
26     const deviceKey = request.header('x-device-key');
27     if (!deviceKey) {
28       throw new UnauthorizedException('Missing X-Device-Key header');
29     }
30     const device = await this.devices.findOne({
31       where: { keyHash: sha256(deviceKey) },
32     });
33     if (!device || device.status !== DeviceStatus.ACTIVE) {
34       throw new UnauthorizedException('Unknown or revoked device key');
35     }
36     request.device = device;
37     return true;
38   }
39 }
